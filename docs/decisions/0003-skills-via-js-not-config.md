# 0003 技能由 JS 插件注册，而不是配置型 MCP bundle

- 日期：2026-11-22
- 状态：生效

## 背景

DSH 官方文档里有一种极简 bundle：「只有 `package.json` + `cordis.patch.yml`，patch 里插一条 mcp-client 行」，不需要写一行 JS。本插件的第一目标（29 个工具可用）用这种方式就够了。

但上游的能力不止工具：三个 `SKILL.md` 教 agent **什么时候**用哪些工具（先建本体、再演进、再浏览），这是上游产品设计的核心。DSH 的技能目录是独立的 Host 服务 `ctx.skills`，技能摘要要进系统提示、正文要按需加载。

## 选项

| 方案 | 工具 | 技能 | 代价 |
|---|---|---|---|
| A. 纯配置型 bundle | ✅ 一行 patch | ❌ 技能进不了目录 | agent 只能看到 29 个光秃秃的工具名，不知道先建再用 |
| B. 只配 MCP + 把 SKILL.md 当普通文件放仓库 | ✅ | ❌ | 用户得自己 `@` 文件，等于没接入 |
| C. 配置型 bundle + 一个 JS 插件只做技能注册（选中） | ✅ | ✅ | 多一个 `index.js`（174 行）和它的维护面 |

## 决策

选 **C**。`cordis.patch.yml` 里两行：`@noah/dsh-evoontology`（JS，注册技能 + 铺核心）、`@deepseek-ai/dsh-mcp-client`（配置，暴露工具）。

## 理由

工具与技能是两类不同的扩展点，DSH 没有「配置里顺带注册技能」的写法。用 174 行 JS 换取「agent 在正确时机主动命中技能」，是这次移植里性价比最高的一笔投入。

同时确认**不**使用 `ctx.systemPrompt.section` 兜底：同层重名或 `order` 非有限值会直接抛错，且与技能目录重复注入，属于用更弱的机制做同一件事。

## 代价

- 插件从「零代码」变成「有一个 JS 文件」，需要跟 DSH 的 `ctx.skills` 契约走，上游改技能格式时要跟着改解析。
- 技能内容与工具名强耦合：工具名带 `mcp__evo__` 前缀，改 `serverName` 必须重跑同步脚本。
