# 演进本体

进化的本质不是"让模型多想几轮"，而是**把使用中的分歧变成带证据的版本差异**。所以这条链是这样闭合的：

```
用法 → 证据 → 分歧 → 修正 patch → 人确认 → 新版本
```

## 一、先找到分歧

分歧来自三种地方，都要有据可查：

1. **同一问题两个答案**：用户问过类似问题两次，口径不同。
2. **记录与数据不符**：evidence 的 `probe` 重跑结果和 `result` 对不上（数据变了）。
3. **记录缺失导致猜**：回答里出现了"我假设 / 大概是"这类措辞。

把这三类落成具体的节点 id：是哪个 term 错、哪个 mapping 缺、哪个 constraint 不成立。**没有节点 id 的分歧不许进 patch。**

## 二、修正 patch 的写法

- 每条修正必须带新 evidence（新的 `ev.*` 节点，`probe` 是这次真实跑过的），旧证据保留——证据是历史，不是草稿。
- 节点 id 保持稳定：改内容用同一个 id，改逻辑（一个 term 拆成两个）才新增 id 并把旧的 `remove`。
- `summary` 写"为什么这一版比上一版好"，`limitations` 写"这一版仍然不知道什么"。这两项是给人评审的唯一线索。
- 一次只推进一个可判定的改动。想同时改五件事，就说明还没找到主要矛盾。

## 三、判定"变好了"的标准

下面任一条成立才算进化有效，否则这次 patch 只是换了个说法：

- 原来答错/答不出的问题，现在能答且能指出依赖哪条约束；
- 原来靠猜的口径，现在有 evidence 支撑；
- 版本 diff 更小但覆盖的问题更多（说明抽象层次对了）；
- 同样的意图，查询骨架变得更直接（少一次手工换算或手工过滤）。

反过来，**节点变多但没人用的语义 = 膨胀**：没有对应问题的节点，在评审时应该被删掉，而不是留着"以备万一"。

## 四、谁说了算

- 模型可以**提议**任何版本，不能让它自己**生效**：`evo_commit` 产草稿，`evo_publish` 要人确认。
- 评审看的是 `evo_history` 的 diff：新增/删除/修改的节点与边，以及每条新证据的 probe。看 diff 比看新版本全文有效得多。
- 回退是零成本的（`evo_revert`），所以宁可发布后回退，也不要因为怕错而不发布——但**回退的触发条件要事先说清**（比如"如果 v4 让这道题答不出来就回退到 v3"）。

## 五、当前阶段说明

P0 只有 store + 工具 + 手动循环。以下能力**还没有**，不要在回答里假装有：

- 自动跑 Builder / Critic / Evaluator 三个子角色；
- 自动收集使用轨迹（当前要人指出哪次回答有问题）；
- held-out 题集与自动评测；
- 多轮预算与自动停止。

推进循环时如果发现需要这些东西，直接说"这一步需要 P3 的能力"，不要用手工模拟出假象。
