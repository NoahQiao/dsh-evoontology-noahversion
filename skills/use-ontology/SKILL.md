# 用本体

语义层的价值只在"用"的这一刻体现：**同一个问题，两个 agent 应该得出同一个答案，并且能说清为什么**。

## 一、写查询之前

1. `evo_status` — 确认有没有激活版本，节点够不够（计数为 0 或没有激活版本 = 别指望它）。
2. `evo_task_start` — 把这次要回答的问题原话钉在激活版本上。**先开任务再查数据**：之后每次 `evo_query` 都会自动记进这个任务的 `event` 表，任务结束时就有一条"这个问题是靠哪几次查询回答的"的链条。同一会话只允许一个进行中的任务，答完必须 `evo_task_finish`。
3. `evo_resolve` 传用户的分析意图（原话即可）。返回的是：命中的术语、字段映射（含单位换算）、约束（单位/取值范围/口径）、以及只读查询骨架。
4. 命中了就按映射和约束写查询；没命中就换关键词再试一次 `evo_browse`，**不要**因为没命中就假装语义层不存在——把它当作"这里还没有记录"，可以在回答末尾提一句。

**关键**：映射里带 `transform`（如 `value/1000 → W`）时必须换算，不要直接用原始列值；约束说有单位或口径差异时按约束解释，不要按列名字面理解。

## 二、查询只能用 `evo_query`

`evo_query` 是本插件里唯一的执行器，只读、单条语句：

- 支持 `.db` / `.sqlite` / `.csv` / `.tsv` / `.json`；csv/json 会装载成内存表，表名是文件名主干（`mon_4b.csv` → `mon_4b`）。
- 只能 `SELECT` 或 `WITH`；写操作、`PRAGMA`、`ATTACH` 一律被拒（不是提示，是执行层拒绝）。
- 最多 100 行（可调到 500）、单值 2 KB、5 秒超时。要全量统计就写聚合，不要 `SELECT *`。
- 超时是真的被掐掉——所以宁可先 `LIMIT 5` 看形状，再跑聚合。

被拒绝或被掐断的调用也会记进任务事件（`error=1`），这是故意的：任务结束时能看出"试过什么、为什么没成"。

## 三、回答里要带出来的东西

- 用了哪个版本的语义（`v3`），这样别人能复现。
- 结论依赖的关键约束（"pkgW 记为 mW，换算后 27.9–36.6 W"）。
- 如果结论和语义层记录**冲突**（数据变了、或记录本来就错），明确说出来，并给出证据——这比默默给一个数有价值得多。
- 收尾：`evo_task_finish`，把答案写进去。任务记录本身就是"这个版本被用过、且答案在做什么"的证据。

## 四、发现记录不对时

不要原地改结论就完事。正确做法：

1. 用 `evo_query` 拿到新证据（重跑一次 probe，看结果是否变化）。
2. 用 `evo_commit` 提交一个修正 patch（新 evidence + 修正的 term/mapping/constraint），summary 里写清"原来的记录为什么会误导"。
3. 告诉用户"语义层已修正为 vN+1，需要 publish 才生效"。发布是改变线上语义的动作，**要人确认**，不要自己 publish。

## 五、判断标准

一条分析算不算"用好了语义层"：

- 同样的意图，别人只看查询就能判断口径对不对；
- 单位、取值范围、枚举含义没有一处是靠猜的；
- 结论里能指出它依赖哪条约束；
- 如果数据本身变了，能一眼看出哪些结论过期了。

## 六、不要做

- 不要在语义层说了 A 的时候按列名猜 B。
- 不要为了迎合已有记录而删改数据侧的观察。
- 不要把"语义层没记录"说成"数据没有这个概念"——那是两件事。
- 不要在只读查询里加写操作：所有会改数据源的动作都不属于本技能的职责。
